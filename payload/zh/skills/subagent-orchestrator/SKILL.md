# 子代理编排

优化用户要求的最终结果，而不是代理活动。最终结果包括交付物、验收条件和重要约束。先在最小真实任务上证明对用户最关键、也最难的行为，再建设支撑机制。

## 决策与路由

1. 先由主代理处理。记录用户要求的结果、已确认约束、最短直接证明，以及子代理将替代的实质工作，并将其作为验收锚点；安装、子代理收据、测试或审查等中间信号只能作为支持该锚点的证据。
2. 小型工作优先直接调用或批量调用工具。仅委派有界叶子任务：它必须替代主代理的实质工作、用简短收据隔离嘈杂的证据流，或提供必需的独立门禁。复杂度、文件数量、剩余容量或单纯追求更高置信度都不足以构成委派理由。
3. 从宿主提供的角色说明中选择明确的 `agent_type`。狭窄且能替代主代理实质探索的只读代码库问题使用 `explorer`；策略、所有权和验收条件均已确定的实现切片使用 `worker`。不得主动把无法匹配的工作路由给 `default`；应留在主代理。
4. 四个自定义角色仅用于各自的明确任务：

   - `evidence_tester`：一个结构化测试或一组有界的运行手册/日志证据，以及一个指定 artifact；不修改源代码。
   - `boundary_mapper`：一个未解决的跨组件执行、状态或持久化边界；不作设计结论。
   - `risk_reviewer`：针对冻结候选状态中明确的高风险不变量执行一次独立门禁。
   - `risk_reviewer_max`：仅在有效审查仍留下有证据支持的歧义，且该歧义可能改变不可逆的 P0/P1、安全、授权或数据完整性决策时，执行一次终态升级裁决。

5. 仅在实际启动子代理时阅读[委派契约](references/delegation-contracts.md)。在编排调用中设置所选角色，要求返回供模型读取的英文收据，并将交接内容限制在任务局部事实内。验收已经返回的子代理结果时，依据其范围、证据、新鲜度和角色边界判断；不得仅因角色元数据缺失或为 `default` 就丢弃结果，也不得只为修正标签而重新启动子代理。
6. 主代理必须继续承担实质工作，并保留授权、范围、单一写入者整合、冲突解决、审查发现裁决和最终验收权。如果主代理主要在协调、轮询或等待，就减少委派并直接完成工作。

## 约束执行

- 允许委派时先启动一个子代理。只有任务有界、相互独立、所有权安全，并预期减少耗时或降低根上下文噪声时，才增加普通首轮的第二个子代理。普通上限为两个子代理和一个活动写入者；写入范围不得重叠。
- 每个子代理都必须是叶子。禁止子代理继续委派或跨子代理协作。使用已安装的子代理模型和推理设置，不按任务重新调参。
- 使用宿主支持的最小任务局部上下文分叉。操作叶子只接收所需的有界近期上下文；新审查者不接收父级 turn。上下文分叉不是模型选择器，也不会授予权限。提出路由或效率主张前，从宿主回读实际子代理模型和推理强度。
- 后续波次、增加写入者、扩大范围或重新运行审查都会打开扩展检查点。先收集并整合当前必需的收据。只有当新证据为下一个子代理提供一个有界且不重叠的目的、实质结果与风险保持不变，且委派成本低于直接完成时，主代理才可不询问并解除至多一个后续子代理。检查点不得放宽叶子拓扑、所有权、写入范围或状态新鲜度规则。
- 仅当用户要求检查点，或证据留下关于结果、验收、外部行为、兼容性、安全、隐私、架构、重要成本、迁移或不可逆影响的实质性用户选择时询问。报告能力或访问阻塞及其下一位负责人或下一步动作；不要把阻塞伪装成偏好。
- 如果授权被拒绝或已过时，但受影响的动作并非交付叶子结果所必需，子代理应继续完成其余安全且范围内的工作，并在终态收据中报告阻塞项。只有该动作阻断所分配的结果时，才提前返回一份终态 `approval-blocked` 收据。在宿主证据证明存在适用于子代理的可复用授权前，不得重复该受阻动作，也不得把相同权限类别和所有者范围的边界分配给其他子代理。
- 若两次面向决策的尝试仍未改变同一不确定性，就停止尝试其他角色变体，由主代理取得最小区分性观察。

## 审查与收敛

1. 仅在存在明确的高风险不变量或用户明确要求时准入审查。只有写入者全部终止、主代理完成整合和直接检查后才冻结候选状态；任何相关变更都会使此前的门禁结果失效。
2. 分配写入者或审查者前，记录一份紧凑矩阵：每个不变量、最小反例、所属边界或 seam、正向实现证据，以及所需负例、重启或恢复证明。不得用审查者来发现这份矩阵。
3. 冻结一份候选收据，其中包含准确 revision 或状态指纹、相关 diff 或 artifact 指纹、具名不变量指纹和已完成的直接检查。缺少该收据的审查者交接不完整。
4. 审查者是证据门禁，不是设计者或需求来源。主代理依据验收锚点裁决每项发现。缺字段拒绝属于契约重试，不算有效评审；补齐交接后启动新审查者，不得 follow up 已拒绝的审查者。
5. 修复已接受的阻塞，直接验证，重新冻结并执行一次新复核。如果仍然阻塞，停止自动审查循环并回到第一性原理。再次独立审查必须有变更后的候选状态或新的区分性证据，并经过新的扩展检查点。
6. 明确要求的多重审查限为一个批次：最多三个新审查者，针对同一冻结状态中的互不重叠不变量；不得投票或举办设计工作坊。`risk_reviewer_max` 只能通过前述升级路径使用，不得作为常规第二意见。

## 以证据收尾

- 抽样核验子代理证据及其负责的 artifact，不重放扫描。确认执行过程符合所选角色和范围。静态策略测试只能证明本地一致性；安装和客户端回读只能证明已加载，不能证明生产效率。源代码层证据标记为 `verified-local`。
- 只有取得与验收锚点中的主张相匹配的证据、明确放弃或替代原结果，或出现真实的用户级阻塞时才收尾。子代理终态、门禁结论、安装、测试或预算耗尽只能关闭其自身的子边界。
- 当编排开销接近其替代的工作量时停止委派。在真实任务证明有必要之前，不要新增 harness、schema、安装器功能、授权系统、审查层级或 benchmark。

仅在增加第二个子代理、进入后续波次、发生自定义角色转换或开展审查时，阅读[高级路由策略](references/routing-policy.md)。仅在实际比较路由或提出效率主张时，阅读[评估策略](references/evaluation-policy.md)；它不约束 Skill 的日常执行。
